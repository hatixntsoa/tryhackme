## 1. Executive Summary

An internal photo gallery ("Meridian image library") stopped serving images. Examination of the preserved disk shows the cause was a **ransomware-style intrusion that took roughly one second to execute**.

1. An authenticated user abused the album **export** API. The `selection` JSON field is concatenated into a shell command passed to `subprocess.run(..., shell=True)`, which gives **command injection**.
2. The injected command downloaded an ELF binary from `10.0.2.2:18081`, stored it as a hidden file in the service account's cache directory, made it executable and ran it.
3. The binary encrypted every image with **AES-256-GCM** using a key generated by **SplitMix64**, seeded with the **current Unix time in milliseconds**.
4. The seed is not stored anywhere, but it is a 13-digit timestamp. The timestamp is bounded by forensic artifacts (database and inode timestamps). That reduces the key search to a few thousand candidates, which makes the files fully recoverable.

The flaw is a design weakness: the key comes from a predictable, low-entropy source, so the encryption is reversible without the attacker's cooperation.

---

## 2. Analyst Rules of Engagement

The brief required that the disk be examined **without modification** and the executable analyzed **without execution**. All work followed those rules:

- `disk.img` was only read, using TSK tools, which operate read-only on the image.
- Every extracted artifact was written to `~/work/`.
- The malware was analyzed statically (strings, imports, Ghidra). It was never executed.

## 4. Objective 1: How Was the Application Compromised?

### 4.1 Source code review

```bash
mkdir -p ~/work && cd ~/work
icat -o 2099200 ~/Desktop/artifacts/disk.img 263163 > gallery.py
grep -nE "route|subprocess|os\.system|popen|shell=True" gallery.py
```

The grep surfaces `subprocess.run(command, shell=True, ...)` at line 161. The surrounding function is the export worker:

```python
def export_job(job_id, selection):
    filename = job_id + ".tar"
    destination = EXPORTS / filename
    # The legacy name selector is interpolated by this application's export worker.
    command = f"/bin/tar -cf '{destination}' -C '{ORIGINALS}' {selection}"
    process = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=45)
```

`selection` is user-controlled and unquoted, and it is placed into a shell command string. It is fed by this route:

```python
@app.post("/api/albums/<int:album_id>/export")
@authenticated
def export(album_id):
    if album_id != 1:
        abort(404)
    body = request.get_json(silent=True) or {}
    selection = body.get("selection", ".")
    if not isinstance(selection, str) or len(selection) > 1000:
        abort(400)
```

Validation is limited to a type check and a length check, with no allow-list. Only album `1` exists, so the literal abused path is:

**Answer, Question 1: Which application endpoint was abused to execute commands on the server?**

```text
/api/albums/1/export
```

> **Weakness class:** CWE-78 (OS Command Injection) and CWE-77. A secondary issue is that the endpoint requires authentication, so the attacker needed valid credentials.

### 6.2 Static triage (no execution)

```bash

objdump -T indexd.bin | grep -iE "EVP|SHA|MD5|PKCS|RAND|rand|crypt"
```

Key findings:
- Dynamically linked against **`libcrypto.so.3`** (OpenSSL), so it uses a library rather than a hand-rolled cipher.
- Crypto imports: `EVP_aes_256_gcm`, `EVP_EncryptInit_ex`, `EVP_EncryptUpdate`, `EVP_EncryptFinal_ex`, `EVP_CIPHER_CTX_ctrl` (the GCM tag and IV length controls), `RAND_bytes`, `OPENSSL_cleanse`.
- System imports that signal the design: `gethostname`, `geteuid`, `clock_gettime`, `renameat2`, `pwrite`, `ftruncate`, `futimens` (timestomping), `fsync`.
- Embedded strings: `%s.locked`, `/srv/gallery/media/originals`, the three hard-coded filenames (`yard_0147.jpg`, `yard_0148.jpg`, `yard_0152.jpg`), `RESTORE.txt`, `processed=%u`, and the ransom note text.

### 6.3 Encryption algorithm

`EVP_aes_256_gcm` is imported and, in the decompilation, passed as the cipher to `EVP_EncryptInit_ex`.

**Answer, Question 4: Which encryption algorithm and mode protected the images?**


### 6.4 Ghidra: `main` (`FUN_001019fe`)

The entry point is `0x101420`. The first argument of `__libc_start_main` is `FUN_001019fe`, which is `main`. Its logic:

1. **Environment guards (the binary is targeted):**
   - `gethostname()` must equal `"gallery"`.
   - `geteuid()` must be **non-zero**, so it deliberately refuses to run as root.
   - The target directory is opened, and each of the three files must be a regular file, have a link count of 1, be owned by the effective user and fit a size limit.
2. **Seed creation:**
   ```c
   local_200 = local_1f8.tv_sec * 1000 + (ulong)local_1f8.tv_nsec / 1000000;
   ```
   This is the wall-clock time in **milliseconds since the Unix epoch**, a 13-digit integer.
3. **Key derivation:** a loop runs four times, calling `FUN_00101509(&local_200)` for 8 bytes of output and `FUN_00101554` to write them. 4 × 8 = **32 bytes, an AES-256 key**.
4. **Encryption:** `FUN_00101574(dirfd, name, key)` is called for `yard_0147.jpg`, `yard_0148.jpg` and `yard_0152.jpg`, in that order.
5. **Cleanup and note:** `OPENSSL_cleanse` wipes the key from memory, `RESTORE.txt` is written, and `processed=3` is printed.

### 6.5 Ghidra: PRNG (`FUN_00101509`) is SplitMix64

```c
uVar1 = *param_1 + 0x9e3779b97f4a7c15;
*param_1 = uVar1;
uVar1 = (uVar1 >> 0x1e ^ uVar1) * -0x40a7b892e31b1a47;   // 0xbf58476d1ce4e5b9
uVar1 = (uVar1 >> 0x1b ^ uVar1) * -0x6b2fb644ecceee15;   // 0x94d049bb133111eb
return uVar1 >> 0x1f ^ uVar1;
```

These are the standard SplitMix64 constants. Ghidra displays two of the multipliers as negative numbers because it prints them in two's complement. `FUN_00101554` writes the 8-byte value **little-endian**.

SplitMix64 is a fast, **non-cryptographic** generator. It is fully deterministic: the same seed always produces the same key.

### 6.6 Ghidra: encryption routine (`FUN_00101574`)

For each file the routine does the following:

1. Reads the whole file and checks it starts with the JPEG magic `FF D8 FF`.
2. Builds the header: `"GPH1"`, version byte `0x01`, then the **original file size** as a little-endian 64-bit value at offset 8.
3. Generates a **random 12-byte nonce** with `RAND_bytes` at offset `0x10`.
4. Sets up GCM with a 12-byte IV (`EVP_CIPHER_CTX_ctrl(ctx, 9, 0xc, 0)`) and the key.
5. Feeds the first `0x1c` bytes of the header (magic, version, size, nonce) to GCM as **AAD** (`EVP_EncryptUpdate(ctx, NULL, ..., in_00, 0x1c)`).
6. Encrypts the plaintext into offset `0x30`.
7. Writes the **16-byte tag** at offset `0x1c` (`EVP_CIPHER_CTX_ctrl(ctx, 0x10, 0x10, in_00+0x1c)`).
8. Writes the buffer back **in place** (`pwrite`), truncates, `fsync`s, **restores the original atime/mtime** (`futimens`, anti-forensic timestomping) and renames the file to `<name>.locked` with `renameat2`.

The resulting `.locked` file format:

| Offset | Size | Field |
|---|---|---|
| `0x00` | 4 | Magic `GPH1` |
| `0x04` | 1 (+3 padding) | Version `01` |
| `0x08` | 8 | Original size (LE) |
| `0x10` | 12 | GCM nonce (random) |
| `0x1c` | 16 | GCM tag |
| `0x2c` | 4 | Zero padding |
| `0x30` | n | Ciphertext |

Check against the evidence: `yard_0147.jpg.locked` is 278,658 bytes and the original is 278,610 bytes. The difference is 48 bytes, exactly the header (`0x30`).

## 7. Objective 3 (continued): Recovering the Seed

### 7.1 Why this is recoverable

- The nonce is random but stored in plaintext in each file.
- The only secret is the 32-byte key, and the key is a pure function of a 13-digit millisecond timestamp.
- The attack window is tightly bounded by forensic evidence:
  - the exploit request was logged at **05:36:54.554**,
  - `.indexd` was created at **05:36:54.638** (epoch `1792474614638`), and
  - the filesystem was last written at 05:37:22.

The search space is therefore only a few thousand to tens of thousands of candidates. Even a wide range such as `1792474614000` to `1792474640000` is cheap, since it is only 26,000 candidates.

```bash
date -u -d "2026-10-20 05:36:54" +%s
# 1792474614
```

### 7.2 Known plaintext for validation

`/srv/gallery/exports/8452cfc730ed4198.tar` is an export generated before encryption and contains the original `yard_0147.jpg` (278,610 bytes, the same size as in the `.locked` header). The decrypted output can be compared byte for byte against it.

### 7.3 Brute-force and decryption script

The script re-implements SplitMix64 exactly, then tests each candidate seed. As a fast filter it decrypts the first block with AES-CTR (GCM uses counter value 2 for the first data block) and checks for JPEG magic. Any survivor is verified with the full **GCM authentication tag**, which makes a false positive practically impossible.

```python
import struct, os
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

M = (1 << 64) - 1
def splitmix_key(seed):
    s = seed
    out = b""
    for _ in range(4):
        s = (s + 0x9e3779b97f4a7c15) & M
        z = s
        z = ((z ^ (z >> 30)) * 0xbf58476d1ce4e5b9) & M
        z = ((z ^ (z >> 27)) * 0x94d049bb133111eb) & M
        z = z ^ (z >> 31)
        out += struct.pack("<Q", z)
    return out

def parse(path):
    d = open(path, "rb").read()
    assert d[:4] == b"GPH1"
    return d[:0x1c], d[0x10:0x1c], d[0x1c:0x2c], d[0x30:]   # aad, nonce, tag, ct

aad, nonce, tag, ct = parse("yard_0147.jpg.locked")
ctr_iv = nonce + (2).to_bytes(4, "big")

found = None
for seed in range(1792474614000, 1792474640000):
    key = splitmix_key(seed)
    ks = Cipher(algorithms.AES(key), modes.CTR(ctr_iv)).decryptor().update(ct[:16])
    if ks[:3] == b"\xff\xd8\xff":
        try:
            AESGCM(key).decrypt(nonce, ct + tag, aad)    # full tag verification
            found = seed
            break
        except Exception:
            pass

print("SEED =", found)
if found:
    key = splitmix_key(found)
    print("KEY  =", key.hex())
    os.makedirs("out", exist_ok=True)
    for n in ("yard_0147.jpg", "yard_0148.jpg", "yard_0152.jpg"):
        aad, nonce, tag, ct = parse(n + ".locked")
        pt = AESGCM(key).decrypt(nonce, ct + tag, aad)
        open("out/" + n, "wb").write(pt)
        print("decrypted", n, len(pt))
```

## 13. Root Cause and Recommendations

### Root cause
1. **Command injection** in the export worker. User input was concatenated into a shell command with `shell=True`.
2. **Insufficient input validation.** Only the type and length were checked, with no allow-list of file names.
3. **No detection or egress controls.** The server could reach an arbitrary internal host and download and run a binary from a world-writable-by-service path.

### Remediation (application)
- Remove `shell=True`. Use `subprocess.run([...])` with an argument list, or better, use Python's `tarfile` module and avoid spawning a process.
- Validate `selection` against the `ALLOWED` set of names (the code already has one for downloads) and reject anything else.
- Add rate limiting and audit logging for export requests, and log the real client IP via `X-Forwarded-For` handling.

### Hardening (host)
- Mount `/srv/gallery` with `noexec,nosuid,nodev`. The binary could not have been run from there.
- Restrict outbound network access for the service (systemd `IPAddressDeny=` / `RestrictAddressFamilies=`, or host firewall rules).
- Add `SystemCallFilter=` and `MemoryDenyWriteExecute=` where feasible, and enforce an AppArmor profile for gunicorn.
- Ship logs off-host so an attacker cannot wipe or truncate them.
- Enable auditd rules for execution from hidden directories and for files created under `/srv/gallery/.cache`.

### Detection ideas
- Alert on web-app processes (`gunicorn`) spawning `sh`, `curl`, `wget` or `chmod`.
- Alert on executable files created in service-account cache directories.
- Alert on mass file renames to a new extension (`*.locked`) in a short time window.

### Resilience
- Keep offline, versioned backups of media. In this case the pre-encryption export archives helped validate recovery, but they should never be treated as backups.

## 14. Lessons Learned

- **A predictable key is no key.** Seeding a non-cryptographic PRNG with the clock gives an attacker's key only about 20 to 30 bits of useful entropy once the time window is known. Keys must come from a CSPRNG (`RAND_bytes`, `getrandom`). The malware author used `RAND_bytes` for the nonce but not for the key, which is the mistake that made recovery possible.
- **Forensic timestamps bound cryptographic search spaces.** Database records and inode times narrowed the seed to a window of seconds, so brute force took moments.
- **Authenticated encryption doubles as an oracle.** The GCM tag turned each candidate key into an exact yes/no test, with the known-plaintext export archive as an independent check.
- **Look past the obvious log.** The nginx log was empty, but the application's own SQLite database (including its WAL file) held the full story of the attack.
